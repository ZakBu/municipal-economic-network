# Подключение Codex и других AI-агентов

Эта страница — единая точка входа для участника, который передаёт проект AI-агенту.
Репозиторий публичный: чтение кода и документов не требует GitHub-авторизации.
Изменение репозитория, Issues, Pull Requests и Kanban выполняется от GitHub-аккаунта
конкретного участника и требует его собственной авторизации и прав доступа.

## Готовый стартовый промпт

Скопируйте весь блок в новый чат Codex. Если проект ещё не клонирован, приложите ссылку
на репозиторий. Не вставляйте токены, пароли и приватные ссылки на данные.

```text
Работай с публичным репозиторием:
https://github.com/ZakBu/municipal-economic-network

Kanban проекта:
https://github.com/users/ZakBu/projects/1

Если репозиторий ещё не открыт локально, клонируй его и открой корень проекта.
Сначала полностью прочитай AGENTS.md, затем README.md, docs/PROJECT.md,
docs/TEAM_GUIDE.md, docs/AI_AGENT_ONBOARDING.md и Issue текущей задачи.
Проверь git status, текущую ветку, remote, GitHub-авторизацию и доступ к Project #1.
Запусти `uv sync --locked` и `uv run python scripts/check_workspace.py`.

Используй repo-scoped BMAD skills из `.agents/skills`:
- `bmad` — определить следующий шаг;
- `bmad-spec` — согласовать многошаговую задачу;
- `bmad-build` — выполнить одну понятную задачу;
- `bmad-code-review` — дополнительное ревью.

GitHub Issues — источник истины для задач, Project #1 — для статусов,
репозиторий — для документов и кода. Не создавай дубликаты документов или задач.
Одна задача = один Issue = одна ветка = один Pull Request.
Перед началом назначь ответственного и переведи карточку в In progress.
После реализации запусти все проверки, открой PR с `Closes #<номер>` и переведи
карточку в Review. Мержи только после успешного CI и требуемого человеческого ревью.
После merge проверь закрытие Issue, статус Done и актуальность связанных документов.

Не выбирай научную методологию без отдельной согласованной задачи.
Не коммить большие данные, секреты и персональные данные.
Отвечай и веди документацию по-русски; код и идентификаторы — по-английски.
Если прав не хватает, выполни все доступные локальные и read-only шаги, затем точно
сообщи пользователю, какое разрешение или роль нужны и для какой операции.
```

## Что агент должен проверить в начале

```bash
git remote -v
git status --short
gh auth status
gh repo view ZakBu/municipal-economic-network
gh project view 1 --owner ZakBu --format json
uv sync --locked
uv run python scripts/check_workspace.py
```

Ожидаемый `origin`:
`https://github.com/ZakBu/municipal-economic-network.git`.
Команда `gh project view` требует OAuth scope `project`. Если его нет, участник один раз
выполняет `gh auth refresh -s project` и подтверждает вход в браузере. Это действие нельзя
перенести в репозиторий или выполнить за другого пользователя.

После проверки агент должен кратко сообщить:

- текущую ветку и наличие локальных изменений;
- доступ на чтение/запись в репозиторий;
- доступ к Project #1;
- выбранный Issue и его текущий статус;
- следующий безопасный шаг.

## Модель доступа

| Возможность | Без входа | GitHub-аккаунт | Дополнительное условие |
|---|---:|---:|---|
| Читать и клонировать репозиторий | Да | Не нужен | Репозиторий публичный |
| Читать публичные Issues и PR | Да | Не нужен | — |
| Создать Issue/комментарий | Нет | Нужен | Разрешения владельца и настройки GitHub |
| Отправить PR из fork | Нет | Нужен | Fork пользователя |
| Писать прямо в ветки репозитория | Нет | Нужен | Роль Collaborator с write-доступом |
| Читать/редактировать Kanban | Зависит от видимости | Нужен для записи | Доступ к Project #1 и scope `project` |
| Мержить PR | Нет | Нужен | Write/maintain-доступ и выполненные правила merge |

Публичность проекта не выдаёт права записи. Каждый участник работает под своим аккаунтом;
агент использует только уже авторизованный на его компьютере GitHub CLI.

## Источники истины

| Объект | Источник | Что обновляет агент |
|---|---|---|
| Постановка и границы проекта | `docs/PROJECT.md` | Только через согласованный PR |
| Инструкции агентам | `AGENTS.md` | При изменении общего процесса |
| Задача и критерии приёмки | GitHub Issue | Прогресс, блокеры, ссылки на PR/ADR |
| Статус работы | GitHub Project #1 | Backlog → Ready → In progress → Review → Done |
| BMAD-планы | `_bmad-output/` | Артефакты выбранного workflow |
| Решения команды | `docs/decisions/` | ADR после принятия решения |
| Идеи | `docs/ideas/` | Неоформленные предложения |
| Эксперименты и выводы | `docs/EXPERIMENTS.md`, `docs/RESULTS.md` | Только проверяемые записи |
| Код, тесты, конфиги | `src/`, `tests/`, `config/` | В рамках текущего Issue |

Если сведения расходятся, Issue определяет объём текущей задачи, ADR — принятое решение,
а код и тесты — фактическое поведение. Агент отмечает конфликт и исправляет источники
в том же PR либо создаёт отдельный Issue, если это выходит за текущий объём.

## Автоматический цикл задачи

1. Найти карточку в `Ready`, прочитать Issue и зависимости.
2. Назначить ответственного; не брать задачу, уже выполняемую другим участником.
3. Обновить `main`, создать ветку `feat/<issue>-<slug>`, `fix/...` или `docs/...`.
4. Для одной сессии использовать `bmad-build`; для крупной задачи сначала `bmad-spec`.
5. Реализовать только критерии Issue, сохраняя чужие изменения.
6. Запустить workspace check, тесты, lint и проверку форматирования.
7. Закоммитить, отправить ветку и открыть PR с `Closes #<issue>`.
8. Перевести карточку в `Review`, дождаться CI и обработать замечания.
9. После требуемого человеческого ревью выполнить squash merge и удалить ветку.
10. Проверить, что Issue закрыт, карточка в `Done`, документы и ссылки актуальны.

Rebase допустим для личной ветки до ревью. Не делать rebase/force-push ветки, которую
использует другой участник, без его явного согласия. Не делать force-push в `main`.

## Если участник не является Collaborator

Агент создаёт fork в аккаунте участника, добавляет upstream на основной репозиторий,
создаёт ветку в fork и открывает Pull Request в `ZakBu/municipal-economic-network:main`.
Карточки Kanban меняет владелец или участник с доступом к Project; отсутствие такого доступа
не мешает подготовить код и PR. В PR нужно указать Issue и желаемый статус карточки.

## Передача работы другому агенту

Перед завершением незаконченной задачи агент оставляет комментарий в Issue:
что сделано, какая ветка/PR, какие проверки прошли, что осталось и что блокирует.
Новый агент начинает с Issue и фактического состояния ветки, а не с пересказа старого чата.
