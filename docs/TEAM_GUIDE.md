# Как работать вместе

## 1. Первое подключение

Владелец приглашает участников через Settings → Collaborators. Каждый принимает приглашение,
клонирует репозиторий по README, выполняет `uv sync --locked` и открывает папку в Codex.
У каждого своя рабочая копия и свой аккаунт; общий контекст хранится в файлах GitHub.
Чаты Codex сами по себе не становятся общей памятью команды.

Проверьте установку командами из README. Попросите Codex прочитать AGENTS.md и объяснить структуру.
BMAD skills уже находятся в проекте: заново скачивать их каждому участнику не нужно.

## 2. Начало каждой задачи

Сначала выберите Issue и назначьте себя ответственным. В Issue должны быть:
ожидаемый результат, критерии приёмки, входные материалы и зависимости от других задач.
Согласуйте с коллегами общие файлы, если они затронуты несколькими задачами.

```bash
git switch main
git pull --ff-only
git switch -c feat/12-source-registry
```

Число 12 — пример, замените номером своей задачи. Переключайтесь с чистой рабочей копией;
незавершённое изменение сначала сохраните в своей ветке.

## 3. Работа с Codex и BMAD

Для одного понятного изменения:

```text
Используй bmad-build. Прочитай AGENTS.md и Issue #12.
Сначала проверь фактическое состояние проекта. Выполни критерии приёмки,
обнови необходимые документы, запусти проверки и подготовь описание PR.
```

Для задачи, которую надо разделить между участниками:

```text
Используй bmad-spec. Помоги согласовать спецификацию первой версии из docs/PROJECT.md.
Не выбирай научную методологию без обсуждения с нами.
Разбей согласованный объём на независимые задачи с критериями приёмки.
```

Для навигации: «Используй bmad и подскажи следующий шаг».
Не запускайте все роли BMAD подряд ради процесса: выбирайте нужный skill по масштабу задачи.

## 4. Сохранение и передача изменений

```bash
uv run python scripts/check_workspace.py
uv run pytest
uv run ruff check .
uv run ruff format --check .
git status
git add <конкретные-файлы>
git commit -m "feat: add source registry"
git push -u origin feat/12-source-registry
```

Откройте Pull Request на GitHub. Заполните шаблон, укажите `Closes #12`, запросите ревью коллеги.
Зелёный CI подтверждает автоматические проверки, но не заменяет смысловую проверку работы.
После ревью и исправлений используйте Squash and merge. Обновите статус Issue на доске.

## 5. Если работаете параллельно на одном компьютере

Каждой задаче — отдельный worktree и отдельная папка:

```bash
git fetch origin
git worktree add ../men-task-12 -b feat/12-source-registry origin/main
```

Откройте именно эту папку в Codex и выполните `uv sync --locked` внутри неё.
Не направляйте два чата на одни незакоммиченные файлы.
Не запускайте обновление BMAD одновременно с задачами команды.

## 6. Конфликты

В своей ветке выполните `git fetch origin`, затем `git merge origin/main`.
Прочитайте конфликтующие изменения и договоритесь с автором второй задачи о совместном результате.
Не выбирайте автоматически «всё наше» или «всё их». Повторите проверки, закоммитьте и отправьте ветку.
Изменения библиотек требуют согласовать pyproject.toml и пересоздать uv.lock через `uv lock`.

## 7. Где писать мысли и решения

| Ситуация | Действие |
|---|---|
| Появилась идея | Короткая запись в docs/ideas/inbox.md с автором |
| Нужно выполнить работу | Issue с ответственным и критериями |
| Нужно обсудить текущую задачу | Комментарий к Issue/PR |
| BMAD создал спецификацию | Сохранить в _bmad-output/ и связать с Issue |
| Принято общее решение | ADR из docs/decisions/000-template.md |
| Проведён эксперимент | Запись в docs/EXPERIMENTS.md со ссылкой на артефакты |
| Есть подтверждённый вывод | docs/RESULTS.md |

Git синхронизируется через commit/push/pull, а не посимвольно в реальном времени.
Короткие обсуждения могут идти в Telegram; вывод не должен оставаться только в чате.
